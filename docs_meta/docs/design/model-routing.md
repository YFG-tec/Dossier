## 为什么值得做

三周的账：重模型跑的活里，有一格是「跑格复核」——把验收命令再跑一遍、把读数填进表。这是形状判定，
不需要构思。`hooks.md` §2 那张分工表 2026-09-10 就画好了（钩子/便宜模型/贵模型各管哪格），
`check-verdict.sh`（5.3 产物）已经把其中「无模型」那一格吃掉了；剩下的格子该按同一张表派。

## 形状（草案）

- **卡上不加新字段**。「档位」已有（重/轻），模型路由**沿档位走**，不另立一根轴——
  轻刀的格复核与巡查 → 便宜档；写卡、建造、审查、动 `src/` 条文的刀 → 重档。宪法刀恒重。
- **路由住代理席**。派单时按卡的档位选 Saved Agent（自定义模型绑定在应用侧，2026-10-02 人确认「都能通」）。
  路由本身不进 `src/` 条文——它是代理席的调度自由度，写进 roles.md 代理席一格即可，一格不立新节。
- **便宜档只领两类活**：①复跑验收命令并回填读数（不改判据）；②巡查读盘。**不领**：审卡、验收结论、
  任何「过/不过」的签字。签字恒归重档或命令本身（`check-verdict.sh` 已经是命令了）。
- **驯化对冲不变**：便宜档报「全绿」时，重档抽查（影子模式同款：不一致记谁对）。

## 判据候选（裂行时定死）

- 代理席派单记录里，轻刀的格复核出现便宜档模型名 ≥1 次/刀；
- 便宜档回填的读数与重档抽查一致率（影子一个月后报）；
- `run.sh` 本数不涨（模型路由不新增检查本）。

## 错法

错在「便宜」和「重」的界可能切不准：格复核看似机械，遇到 red 归因（trace 假红那族）其实要判断——
那种格子要收回重档。先跑影子，别先立死。
