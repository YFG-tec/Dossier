## 留白人 2026-09-14 裁完了，两处变三处，再加一个默认值

原话逐字，按说出的先后排：

> 两项留白都由人决定，另外要往那个目录展开也由人决定

> 当然默认是以submodule 挂在主目录下，直接运行脚本在外面一层展开

> 这个比较自由

**前一句定的是权归谁：三样都归人给。后两句补的是默认值：母本给一个默认，但不锁死。**
两句不冲突——**默认不是规定**，人不指就照默认走，人指了就照人的。

| 哪一样 | 权归谁 | 默认值 | 出处 |
|---|---|---|---|
| 子模块挂宿主哪个路径 | 人给 | **宿主主目录下**（宿主根的直接子目录） | 本裁（原留白一） |
| 骨架往哪个目录展开 | 人给 | **子模块目录的外面一层**，即宿主根 | 本裁新增 + 同日补默认 |
| 升级那一步 git 动作谁跑 | 人跑 | 无默认可给，母本不代跑 | 本裁（原留白二） |

第二样是人自己补出来的，**不是本席摆的留白**。它比另外两样重：
另外两样只影响 `form.md` 的措辞，这一样改的是 `init` 这个动作的形状——
落点从「母本写死的位置」变成「带默认值的参数」。
**默认值本身是相对路径，不是绝对位置**：脚本在子模块里，往上一层铺，所以它不需要知道宿主叫什么、在哪。

**这一条和业内对得上，不是新发明。** `git submodule add <url> <path>` 的路径是参数，
`specify init <name>` / `init --here` 的落点也是调用者给的，两家都是「有默认、可覆盖」。
母本一处也不用自己造。

**代价照记：**

- 有默认就有人不看默认，宿主之间路径仍会不一致；文档举例只写默认那一种。
- 升级要两条命令，不是一条，不如「一键升级」顺手。
- 落点是参数，`2.8c` 的生成器得校验人给的路径，也得算得出「外面一层」是哪一层。

**四样都落在 `form.md` 的措辞里，`paradigm.md` §4 那四行的字面不受影响**——
新字面本来就没写死任何一个路径，默认值也不往 §4 里写。**§4 说边界，不说路径。**
